# Методология locqa

Как `locqa` находит ошибки локализации в ARB-файлах, как исправляет их и как мы честно измеряем качество. Все примеры в этом документе синтетические: данные кейса в репозиторий не попадают.

## 1. Постановка

На входе исходный файл (`intl_ru.arb`), перевод (`intl_kk.arb`), необязательный глоссарий и необязательные «пивоты»: другие переводы тех же ключей (`intl_en.arb`, `intl_uz.arb`). На выходе:

| Артефакт | Что внутри |
|---|---|
| `report.json` | Список находок по схеме кейса: `key, issue_type, severity, source, target, evidence, suggestion, confidence, reviewed_by_human` |
| `report.html` | Самодостаточный отчёт: фильтры, поиск, дифф предложений, тепловая карта по разделам |
| `report.full.json` | Всё: метаданные, сводка, находки, советы ниже порога, lint |
| `intl_kk_fixed.arb` | Исправленный файл; у каждого изменённого ключа в `@key` стоит `x-locqa.reviewed_by_human: false` |
| `*.review.csv` | Лист для носителя языка: исходник, en, было, стало, причина, пустая колонка вердикта |

## 2. Архитектура

```
ARB (с дублями и @@comment) ─► ArbDocument ─► CheckContext ─► 11 детекторов ─► слияние ─► порог ─► отчёты
                                                     ▲                                          │
                                           глоссарий, пивоты                             locqa fix ─► повторная проверка ─► fixed.arb
```

- **Чтение ARB без потерь.** Строгий JSON-парсер оставляет только последний `@@comment` и последний дубль ключа. Наш сканер сохраняет порядок, все повторы и позиции, поэтому разделы файла (`@@comment`) становятся контекстом находки, а запись правок меняет только нужные байты. Дифф исправленного файла чистый.
- **ICU-парсер** в диалекте Flutter (escaping выключен по умолчанию): плейсхолдеры, `plural/select/selectordinal`, CLDR-категории по локали. Парсер не падает, а собирает ошибки.
- **Детекторы независимы.** Каждый детектор — маленький класс с `run(ctx)`. Ошибка одного детектора не роняет проверку: она попадает в `detector_errors`.
- **Слияние.** Для пары (ключ, тип) остаётся самая уверенная находка, остальные детекторы перечислены в `extra.also_reported_by`.
- **Порог.** В `report.json` попадают находки с `confidence ≥ 0.5`. Остальное хранится в списке advisory для ревьюера: так мы держим точность высокой и не теряем сигналы.

## 3. Детекторы

Правила и статистика по самому файлу; LLM не требуется. Языковые проверки берут профиль языка и молчат для незнакомых языков, поэтому инструмент работает на любой паре.

| Тип | Как ищем | Как держим точность |
|---|---|---|
| `untranslated` | Ключ отсутствует, пустое значение, значение не строка | Пустые «фрагменты» (prefix/suffix, одиночный предлог) — только advisory, если пивоты тоже пустые |
| `same_as_source` | Перевод совпадает с исходником, затем классификация | Пропускаем числа, бренды, имена и заимствования, которые встречаются в настоящих казахских строках файла. Флагуем русские служебные слова и окончания (`-ые`, `-ия`) и строки, которые в другом ключе переведены (это и есть подсказка) |
| `placeholder_mismatch`, `plural_mismatch` | Сравнение множеств аргументов ICU, опечатки (`{levl}`), снятые скобки (`time` вместо `{time}`), структура plural/select, категории CLDR | Голое слово, которое и в исходнике стоит текстом, не считается снятыми скобками |
| `glossary_violation` | Глоссарий со стемингом: варианты, запрещённые формы, бренды | Совпадение по основе с учётом казахских аффиксов (`отбасы` ↔ `отбасының`) |
| `inconsistent_term` | Частые исходные термины выравниваются на казахскую основу по Dice; ключи с другим словом — выбросы. Плюс дубли ключей с разными значениями | Нужны ≥3 ключа и доминирование ≥70 %. Варианты из глоссария и «вторые устойчивые переводы» не флагуются |
| `length_overflow` | Только короткие UI-элементы (кнопки, вкладки, заголовки по имени ключа и форме), выбросы по распределению отношения длин; одинаковые «хвосты-наполнители» в нескольких несвязанных строках | Казахский естественно длиннее русского, поэтому сравниваем с распределением по корпусу, а не с константой |
| `suffix_harmony` | Падежный аффикс, приклеенный к плейсхолдеру (`{name}-ға`): для половины значений гармония гласных нарушится. Ошибки гармонии в обычных словах | Предлагаем переформулировку, которая убирает аффикс с плейсхолдера. Номер+дефис+существительное (`{n}-орын`) — норма |
| `orthography` | Латинские гомоглифы внутри кириллических слов; казахские буквы, набранные русскими двойниками (редкое слово, которое схлопывается в частое с `ә ғ қ ң ө ұ ү һ і`); слова, нарушающие сингармонизм | Нужен частый «правильный двойник» в самом файле или нарушение гармонии; заимствования с `в ф ц ч щ` пропускаются |
| `wrong_language` | Скрипт и маркер-слова, узбекские орфографические маркеры (`o‘`, `g‘`, `’ni`), совпадение с переводом пивота | Совпадение с en при том, что и uz оставил английский, — advisory |
| `machine_translation_suspect` | Файл сам себе словарь: основы, которые часто встречаются вместе в парах ru↔kk, считаются переводами друг друга (Dice). **Заимствованный перевод**: текст ключа дословно взят из другого ключа, чей исходник объясняет слова перевода, а пивот en подтверждает, что смыслы разные. **Несвязанный перевод**: ни одно содержательное слово исходника не передано. **Неверный смысл** коротких строк — только advisory | Пара не может подтверждать сама себя (leave-one-out Dice); привычный перевод, повторённый в ≥4 ключах, не считается подменой; другой скрипт отдаётся `wrong_language` |
| `lint` (вне таксономии) | Дубли ключей и конфликтующие дубли, лишние ключи, теги `<g>`, переводы строк, пробелы | Отдельный список, не разбавляет основной отчёт |

### Severity

- **high** — ломает интерфейс или очевидно неверно для игрока: сломанный плейсхолдер, непереведённый текст, другой язык, переполненная кнопка, неверный падеж после имени игрока, подменённый смысл.
- **medium** — неверный термин, смысл или согласованность.
- **low** — стиль.

### Confidence

`confidence` — оценка детектора, что находка реальна. Она складывается из явных факторов: длина строки, размер чистого большинства, подтверждение пивотом, частота «правильной» формы в файле. Каждый фактор отражён в `evidence`, поэтому любую находку можно проверить, не читая код.

## 4. Исправления (`locqa fix`)

1. Источник правки: файл override (ревьюер, переводчик или LLM; высший приоритет) либо `suggestion` самой находки с `confidence ≥ 0.7`.
2. Правка обязана сохранить плейсхолдеры исходника и разбираться как ICU. Иначе — `rejected`.
3. Исправленный файл **проверяется заново всеми детекторами**. Если правка вскрыла вторую проблему (снятые скобки вернулись, и аффикс оказался приклеен к `{min}`), берётся предложение новой находки — один раз. Если ключ стал хуже, правка откатывается (`rolled_back`).
4. Отсутствующие ключи вставляются после соседа по исходнику, порядок файла сохраняется.
5. Каждый изменённый ключ получает в `@key` объект `x-locqa`: `reviewed_by_human: false`, исходный текст, типы ошибок, источник правки, уверенность, обоснование. Поля `x-` допустимы в ARB и игнорируются `flutter gen-l10n`.

Меняются только значения сообщений и метаданные `@key`, поэтому файл компилируется там же, где компилировался исходный. CI-задача `gen-l10n` (`scripts/check_gen_l10n.sh`) прогоняет `flutter gen-l10n` и `dart analyze` на примерах.

## 5. Честные метрики

Список посеянных ошибок есть только у организаторов, поэтому мы измеряем себя сами (`locqa bench`):

1. Проверяем чистый файл — это **baseline**, его находки исключаются из подсчёта точности.
2. `locqa inject` сеет синтетические ошибки каждого типа рецептами, похожими на ручные: снятые скобки, удалённые ключи, вставленный узбекский текст, хвосты-наполнители, русские буквы в казахских словах, приклеенные аффиксы, подмена синонимом, перевод из другого ключа.
3. Проверяем испорченный файл и сравниваем с ключом ответов: recall по типу (ключ **и** тип должны совпасть), точность новых находок. Усредняем по нескольким seed.

Результаты на реальной паре ru→kk (10 ошибок каждого типа × 3 seed, 270 ошибок) — в [docs/BENCHMARK.md](BENCHMARK.md).

Ограничения бенчмарка: синтетические ошибки проще ручных, а часть «ложных» новых находок на самом деле реальные ошибки исходного файла, которые рецепт задел. Поэтому вторая метрика — ручная проверка находок на реальном файле: каждый детектор откалиброван так, чтобы его находки с `confidence ≥ 0.5` были верными по оценке читателя-казаха.

## 6. Общность

- Любая пара языков: `--source en --target kk`, `ru→uz`, `ru→en`. Казахские правила включаются только для `kk`, узбекские маркеры — для поиска узбекского текста.
- Локаль берётся из `@@locale` или имени файла, её можно переопределить.
- Плюрали CLDR для десятков локалей.
- 700+ тестов на синтетических ARB, CI на Python 3.10 и 3.12, GitHub Action с базовой линией по base-ветке, SARIF для code scanning, sticky-комментарий в PR.

## 7. Бонусы

- **Узбекский** — см. [docs/UZBEK.md](UZBEK.md).
- **Латиница 2021** (`locqa translit`): транслитерация казахской кириллицы по алфавиту апреля 2021 года (Ң → Ñ, І → I/ı, Ы → Y, Ц → Ts, Ч → Tş …) с проверкой длины: строки, которые станут длиннее 1.3× исходника, попадают в отчёт.
- **Переформулировка вместо аффикса**: `suffix_harmony` предлагает текст, где плейсхолдер стоит в именительном падеже или после двоеточия.
- **GitHub Action** — `action.yml`.

## 8. Чего мы не делаем и почему

- Не применяем правки молча: даже уверенная правка помечена для человека.
- Не отправляем данные во внешние сервисы: проверка полностью офлайн. LLM-подсказки можно подать через `--overrides`, и они проходят ту же повторную проверку.
- Не храним данные кейса в репозитории: тесты и примеры синтетические.
